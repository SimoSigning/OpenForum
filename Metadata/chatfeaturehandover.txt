2. Existing chatroom architecture

The application uses three chatroom types:

csharp
public enum ChatRoomType
{
    Private = 1,
    Miscellaneous = 2,
    Topic = 3
}


The three types have different purposes.

Type	Purpose	Ownership
Private	Chats created by users for themselves and invited friends	Has an owner
Miscellaneous	General community chatrooms	No owner
Topic	Chatrooms associated with forum topics	No owner
Chatroom entity relationships

The ForumContext contains:

ChatRooms
ChatRoomMembers
ChatMessages

The relevant EF Core configuration currently includes:

csharp
modelBuilder.Entity<ChatRoom>(entity =>
{
    entity.HasKey(r => r.Id);

    entity.Property(r => r.Name)
        .IsRequired()
        .HasMaxLength(100);

    entity.Property(r => r.RoomType)
        .IsRequired();

    entity.Property(r => r.CreatedByUserId)
        .IsRequired()
        .HasMaxLength(450);

    entity.Property(r => r.OwnerUserId)
        .HasMaxLength(450);

    entity.Property(r => r.CreatedAt)
        .IsRequired();

    entity.HasIndex(r => r.TopicId)
        .IsUnique()
        .HasFilter("[TopicId] IS NOT NULL");

    entity.HasOne(r => r.Topic)
        .WithOne()
        .HasForeignKey<ChatRoom>(r => r.TopicId)
        .OnDelete(DeleteBehavior.Cascade);

    entity.HasIndex(r => r.RoomType);
});


The existing relationships for memberships and messages also use cascade deletion.

This is important because deleting a topic should automatically delete its associated chatroom, memberships and messages.

Verify the actual database migration and foreign-key configuration before relying on cascade deletion.

4. Existing leave-room implementation

The current LeaveRoomAsync implementation has already been updated.

It is important to use this version as the reference, rather than older versions of the method.

csharp
public async Task LeaveRoomAsync(int roomId)
{
    string userId = currentUser.GetRequiredUserId();

    ChatRoom room = await GetRoomOrThrowAsync(roomId);

    ChatRoomMember? membership =
        await chatRepository.GetMembershipAsync(roomId, userId);

    if (membership == null)
        throw new InvalidOperationException(
            "You are not a member of this room.");

    IEnumerable<ChatRoomMember> members =
        await chatRepository.GetMembersAsync(roomId);

    List<ChatRoomMember> remainingMembers = members
        .Where(m => m.UserId != userId)
        .OrderBy(m => m.JoinedAt)
        .ThenBy(m => m.UserId, StringComparer.Ordinal)
        .ToList();

    // Only private rooms are deleted when their final
    // member leaves.
    bool deleteRoom =
        room.RoomType == ChatRoomType.Private &&
        remainingMembers.Count == 0;

    string? newOwnerUserId = null;

    // Ownership only applies to private rooms.
    if (room.RoomType == ChatRoomType.Private &&
        !deleteRoom &&
        room.OwnerUserId == userId)
    {
        newOwnerUserId = remainingMembers[0].UserId;
    }

    await chatRepository.LeaveRoomAsync(
        roomId,
        userId,
        newOwnerUserId,
        deleteRoom);
}


The intended behaviour is:

Private rooms: ownership is transferred when necessary, and the room is deleted when its final member leaves.
Miscellaneous rooms: users can leave, but the room remains.
Topic rooms: users can leave, but the room remains.

Topic rooms have no owners.

No changes to this method should be necessary for topic chat functionality.

Topic creation currently looks like this:

csharp
public async Task CreateAsync(TopicCreateView model)
{
    string userId = currentUser.GetRequiredUserId();

    Topic topic = topicMapper.ToEntity(model);
    topic.CreatedByUserId = userId;
    topic.CreatedByUserName = await userService.GetUsernameByIdAsync(userId);

    await topicRepository.AddAsync(topic);
}


Topic deletion currently looks like this:

csharp
public async Task DeleteAsync(int id)
{
    string userId = currentUser.GetRequiredUserId();

    Topic? topic = await topicRepository.GetByIdAsync(id);

    if (topic == null)
        return;

    if (topic.CreatedByUserId != userId)
        throw new UnauthorizedAccessException("You are not allowed to delete this topic.");

    await topicRepository.DeleteAsync(id);
}

6. Desired topic chatroom functionality

Every newly created topic should automatically receive one associated chatroom.

The intended workflow is:

Creating a topic
User creates a topic.
Topic is saved.
An associated ChatRoom is created.
The chatroom receives:
RoomType = ChatRoomType.Topic
TopicId = topic.Id
Name = topic.Title
OwnerUserId = null
The topic and chatroom are persisted consistently.

The chatroom should not have an owner. The topic creator should not receive special chatroom permissions.

Important: CreatedByUserId is required by the current database configuration. Inspect the existing ChatRoom model and room creation code before deciding what value to assign for system-created topic rooms. Do not arbitrarily use "system" without checking the application's constraints.

Entering a topic chatroom

A user should be able to enter a topic chatroom directly from the topic listing.

The proposed button is:

cshtml
<a asp-controller="Chat"
   asp-action="EnterTopicRoom"
   asp-route-topicId="@topic.Id"
   class="btn btn-outline-primary btn-sm">
    Topic chat
</a>


The new action should:

Retrieve the chatroom associated with the supplied topic ID.
Verify that the topic/chatroom exists.
Check whether the current user is already a member.
If not, add the user as a member.
Redirect to the existing OpenRoom action.

This should follow the same general behaviour as joining miscellaneous rooms.

Do not trust a client-supplied room ID or membership status without validating it server-side.

Leaving a topic chatroom

Already implemented.

The existing leave button in Room.cshtml applies to topic rooms as well.

No special topic-specific leave functionality is required.

Deleting a topic

Deleting a topic should automatically delete:

Its associated chatroom.
All chatroom memberships.
All chat messages belonging to that chatroom.

The existing EF Core cascade relationships should handle this.

Verify that the database migration actually reflects the configured cascade relationship.

7. Architectural recommendation

The previous discussion considered two approaches.

Option A: Inject IChatService into TopicService

Proposed dependency:

csharp
private readonly IChatService chatService;


Add a method to IChatService:

csharp
Task CreateTopicRoomAsync(int topicId, string topicTitle);


Then coordinate topic and chatroom creation in TopicService.CreateAsync.

This is the recommended starting approach for the current architecture.

Option B: Introduce a dedicated orchestration service

This would coordinate topic creation/deletion and chatroom creation/deletion.

It provides greater separation between services but introduces additional abstraction.

For the current scope, Option A is preferable unless inspection of the existing architecture reveals a reason to choose otherwise.

Transaction handling

This is an important consideration.

Creating a topic and its chatroom should be atomic.

If topic creation succeeds but chatroom creation fails, the application should not leave behind a topic without its associated chatroom.

Inspect how repositories share their EF Core DbContext and whether they already support transactions.

Prefer a shared database transaction or an appropriate unit-of-work implementation rather than introducing unnecessary transaction infrastructure.

For deletion, the database cascade relationship should handle the associated chatroom automatically.

10. Important development conventions

A few things should be respected throughout the implementation:

Follow the existing layered architecture.
Do not put database logic in controllers.
Do not duplicate existing chatroom functionality.
Reuse existing repository and service methods where appropriate.
Keep ownership exclusive to private rooms.
Topic rooms must remain available when their members leave.
Do not introduce unnecessary abstractions.
Preserve existing SignalR functionality.
Use asynchronous methods consistently.
Respect existing authorization and antiforgery conventions.
Inspect the actual current implementation before suggesting replacements.
